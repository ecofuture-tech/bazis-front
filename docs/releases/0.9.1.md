# bazis-front 0.9.1

A patch of 0.9.0, from its acceptance on two products: a remembered value that no step takes,
the settings of the anonymous uploads, the conflict of a router that defined `GUEST_HOME`, the
row of a live list, and the limits of the file fields. It requires `bazis>=2.17.0`, as 0.9.0
did; the format of the contract stays 11.

## Fixed

- **A `remember` whose value no next step takes no longer fails the lint of the frontend.**
  `bazis_front e2e` declared a constant for every value of a `remember`
  (`const $file = await test.step(…)`), and `npm run lint` refused the one that nothing used
  (`no-unused-vars`) while `check` said nothing. A `remember` now declares the constants of the
  values that a next step takes (`$<name>`), in their places of the answers
  (`const [, $number] = …`); it reads the others without a constant, so the answer must still
  show them. The walk of the scenarios tells which (`Step.taken`); no new issue.
- **The settings of the anonymous uploads are named as `project.env` takes them.** The hint of
  S057, its row in the guide, "Anonymous uploads" and item 8 of Upgrading of 0.9.0 named
  `BAZIS_FILE_UPLOAD_ANONYMOUS=true` and `BAZIS_FILE_UPLOAD_MAX_SIZE`: a line of the
  environment without the prefix of Bazis is not applied. They are
  `BS_BAZIS_FILE_UPLOAD_ANONYMOUS=true` and `BS_BAZIS_FILE_UPLOAD_MAX_SIZE` (and the rate and
  the TTL, `BS_BAZIS_FILE_UPLOAD_ANONYMOUS_RATE`, `BS_BAZIS_FILE_UPLOAD_ANONYMOUS_TTL`).
- **`openItem` waits for the row that a live list receives.** On a page with the socket of
  bazis-ws (`socket:<status>` of `LiveQuery`), a row that the page shown does not have yet is
  awaited for up to 2 s before the search and the next pages: the item that another session of
  the scenario made after the list was read (a guest sends a request, the dispatcher opens it)
  comes with the refetch that its message starts. A row that does not come still fails the
  step; a page without the socket does not wait.
- **A session of `sessionAs` whose context is created after its test ended is closed.** The
  context was put in the sessions of the test only once created: a test that ended (failed,
  timed out) while it was created left it open, or in the sessions of the next test. `test` of
  the helpers now waits for it and closes it as the test ends.
- **A conflict of `update` names the file of bazis-front.** Once written, each conflict is
  listed with its pristine copy of the new version
  (`<path>: the file of bazis-front: .bazis/base/<asset>@<version>/…`), and the message says to
  resolve the markers or to take that file and apply the changes of the product again: the
  lines changed away from a conflict merge without markers, so a router of 0.8 with its own
  `GUEST_HOME`, resolved by its markers only, kept it beside the import of the template of 0.9
  (`TS2440`). `package.json` has no such file (its side of bazis-front has the npm dependencies
  of the assets too): its markers are resolved, then `npm install`. `update --check` writes
  nothing and names none. The guide ("Conflicts") says the same.
- **The step `upload` of the schema of the product names the bodies of the actions**: it
  uploads into a file field of the open form or into a property of the body of an action that
  takes uploaded files (`UploadedFileId`, `list[UploadedFileId]`), as since 0.9.0.

## Changed

- **`FilesField` takes at most `maxItems` files.** A property of a body with a limit
  (`list[UploadedFileId]` with `max_length=10`: `maxItems` of its JSON Schema in the contract)
  gives it to its field (`maxItems` of `RelationField`, set by `relatedField`): the files chosen
  over it are not uploaded (the error of the field, "At most 10 files."), and the drop zone says
  "up to 10 files". Before, the eleventh file was uploaded, spent the rate of the anonymous
  uploads of the guest, and the action refused the body only at the submit (422).
- **A file field names its types as a user reads them.** The drop zone of `FileField` and
  `FilesField` and the error of a refused type showed `accept` as it is
  (`image/jpeg,image/png,image/webp`); they show `JPEG, PNG, or WebP` (`JPEG, PNG или WebP` in
  Russian): the known media types by their names, an extension in capitals, `image/*` as
  `images`, another type as it is. The input still offers the media types of `accept`. New keys
  of the dictionaries: `upload.too_many`, `upload.type.<audio|image|video>`, `upload.up_to_files`.

## Upgrading

```bash
pip install -U bazis-front
python manage.py bazis_front update      # the helpers of e2e/bazis/, file-field, resource, screens, the hooks, i18n, the schemas of the specs
python manage.py bazis_front e2e         # a `remember` without a next step that takes it
```

1. A product whose `project.env` has `BAZIS_FILE_UPLOAD_ANONYMOUS=true` (the hint of S057 of
   0.9.0) has no anonymous uploads: write `BS_BAZIS_FILE_UPLOAD_ANONYMOUS=true` and
   `BS_BAZIS_FILE_UPLOAD_MAX_SIZE`, then `contract` (S057 until then).
2. A router that kept its own `GUEST_HOME` after the update to 0.9.0 (`TS2440` in `tsc`): delete
   it, `screens` generates it in `routes.tsx`; a product that updates from 0.8 now takes the
   file of the template that `update` names for the conflict of `src/app/router.tsx`.
3. A scenario that removed a `remember` only for the lint may remember the value again.
4. A test of the product that read the type of a file field from its text
   (`image/png,image/webp`) reads its names (`PNG or WebP`); the contract tests of the
   components copied by `update` read them so.
