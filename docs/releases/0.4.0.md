# bazis-front 0.4.0

The public screens: the screens of the users who do not log in are generated from the specs.
It requires `bazis>=2.16.0`, as 0.3.0 did. `manage.py bazis_front update` brings the router
of the template, the layout and the helpers of the tests; export the contract again and run
`manage.py bazis_front screens`, `e2e` and `shots` after it.

## What is new

- **A screen is public when one of its `roles` is anonymous** (`anonymous: true` of a role
  of `spec/product.yaml`, which bazis-permit gives a role `for_anonymous`). The specs have no
  key of their own: the roles say who sees a screen, the anonymous one says that a user
  without a session does. A screen without `roles` is not public.
- **The routes of the public screens** are `PUBLIC_ROUTES` of
  `src/screens/generated/routes.tsx`, which `src/app/router.tsx` of the template routes in
  the layout outside `RequireSession`: a user without a session opens them, the other
  screens still send him to the login. The index `/` of a product without a screen there
  leads to the first link of the navigation as before, public when that screen is. A
  product without anonymous roles has `PUBLIC_ROUTES` null and routes as before.
- **The layout without a session.** `AppShell` shows a user without a session the links
  of the public screens only (`public` of a `NavItem`, which the generated navigation sets;
  a group keeps its public links), no tools (the notifications and the live queries need a
  session) and the sign-in in the place of the session (`signIn`, `action:sign-in`), which
  opens the login and comes back to the screen after it. With a session the layout is that
  of before, the public screens among the others. The layout is one route around every
  screen, `RequireSession` within it: it stays mounted between a public screen and a screen
  of a session (the tools keep their state).
- **What a guest may do.** bazis-permit refuses the creates, the changes and the deletions
  of the routes of the entities to anonymous users: a public screen reads, and writes only
  through a custom action of the route set declared `public=True` (limited by the throttle
  of the core, `BAZIS_THROTTLE_PUBLIC`). `check` refuses the rest (below).
- **The contract** (format 7) gives a custom action `public`, whether anonymous users may
  call it (`x-bazis.public` of the OpenAPI).
- **The custom actions of the route set in the scenarios.** A scenario runs a custom
  action of the toolbar of a list (`action: <id>`), not only one of a card; an action of the
  rows (`list.row_actions`) is still run on the card or as a bulk action (P022).
- **The sample** has the anonymous role `visitor`, its public screen `public-tasks` (the
  tasks, with the action `suggest`, `public=True`, which creates a task) and the scenario
  `visitor-suggests-a-task`.

## The checks

- **P035** (error): a scenario of an anonymous role opens a screen that is not public: the
  frontend sends a user without a session to the login.
- **S044** (error): a public screen creates, changes or deletes through the routes of the
  entities (a form, `card.edit`, "add here", the add of a calendar, a create form of a
  dashboard, a deletion, `list.bulk`, `board.move`), which bazis-permit refuses to anonymous
  users.
- **S045** (error): a public screen leads to a screen that is not public, or a card is in
  the layout of a list that is not public as it is (or a public card links back to a list
  that is not public).
- **S046** (error): a custom action of a public screen is not declared `public=True`.
- **S047** (warning): an anonymous role that no screen lists in its `roles`.
- **S048** (error): `src/app/router.tsx` routes the generated screens (it imports
  `@/screens/generated/routes`) without `PUBLIC_ROUTES`: a router of the product changed
  before 0.4.0, whose public screens no user without a session reaches.
- **V020** (error) of `shots`: the router sent the user to the login, the screen was not
  shot. `shots` shoots a screen without `roles` as the roles that log in.
- `shots` takes a 401 of what a screen reads as its `forbidden` state, as a 403: what the
  backend gives only to the users with a session (the users, the files) answers a user
  without one with 401.

## The tests of the package

- The `test` extra requires `bazis-statusy>=2.13.0`: the fixture of the hooks
  (`assets/react/test/fixtures/sample.json`) is captured from the sample with bazis-statusy
  2.13, whose runtime schema of a list has the meta `for_transit`. The assets do not read it:
  a product keeps bazis-statusy 2.12.0 or newer, the version whose protocol they follow.

## Migrating from 0.3

```bash
pip install -U bazis-front
python manage.py bazis_front update      # a router.tsx that the product changed may conflict (below)
python manage.py bazis_front contract    # contract.json of format 7
python manage.py bazis_front check
python manage.py bazis_front screens
python manage.py bazis_front e2e
python manage.py bazis_front shots --no-run
cd frontend && npx tsc --noEmit && npm run lint && npm test && npm run build
```

1. `update` merges a `src/app/router.tsx` that the product changed: a change of the product
   elsewhere merges with the routes of the template, and one of the same lines (the routes,
   the layout) conflicts. Resolve such a conflict by taking the file of the template and
   applying the changes of the product to it again: the side of the product alone drops the
   public routes, which `check` refuses (S048).
   A product that routed the
   screens of its anonymous users by hand (the recipe of the guide of 0.3) lists the
   anonymous role in `roles` of their specs and removes its own routes and layout: `screens`
   routes them.
2. `contract.json` is of format 7: `check` reports `C002` until it is exported again, then
   S046 for the custom actions of a public screen that are not `public=True`.
3. The new issues of `check`: P035 concerns a product whose scenario of an anonymous role
   opens a screen without that role in its `roles` (usual with the screens of the guests
   routed by hand, the recipe of 0.3: list the role in `roles` of their specs); S044, S045
   and S046 only the public screens; the warning S047 any product with an anonymous role
   that no screen lists; S048 a product with a public screen whose router imports the
   generated routes without `PUBLIC_ROUTES`.

## Not in this release

- The registration and the reset of a password: a guest who needs an account is given one.
