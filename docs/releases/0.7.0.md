# bazis-front 0.7.0

The sign-in with Google of bazis-authing 2.8: a `POST` of its init gives the URL of the login
window, a one-time ticket bound to the browser, and the store token is in no URL. It requires
`bazis>=2.17.0`, as 0.6 did; Google needs `bazis-authing>=2.8.0` (the password login works
with 2.6 and later). `manage.py bazis_front update` brings the client and the template;
export the contract again (format 10).

## Breaking changes

- **Google requires bazis-authing 2.8.** Its login action is now `POST` (`google-auth-init`,
  the same `url`); the template offers a login in a window only for the action `google`
  with `POST` (`WINDOW_LOGINS` of `src/app/session.ts`). With bazis-authing 2.7 or older,
  whose Google action is `GET` with the store token in the URL, the login screen of 0.7 has
  no Google button; bazis-front 0.6 and older, the other way round, show no Google with
  bazis-authing 2.8 (their window logins are the `GET` actions, and its init answers 422 to
  a `GET` without a ticket). Update both together.
- **The page must be same-site with the API.** The init sets a `SameSite=Lax` cookie that
  binds the ticket to the browser, and the window is refused without it (400). The template
  is on the origin of its API (the proxy of Vite routes `/api`); a frontend served on another
  origin needs the API on the same site (`app.site.com`, `api.site.com`), CORS with
  credentials, and the window opened on the origin of the API.
- **The contract** (format 10) has no `token_param` in the section `authing`: no flow puts
  the store token in a URL any more. `CAPABILITIES.authing` of `contract.ts` loses the field.

## What is new

- **`api.authInit(path, store)`** (`AuthInit`, `{ticket, url}`, of `@/bazis/client`): `POST`
  of the login action of a service in a window with the store token as the bearer token and
  with the cookies of the browser (`credentials: 'include'`), the only request of
  bazis-authing besides the logout that sends them; an error is an `ApiError` (401: the
  store is gone).
- **The login in a window** (`loginInWindow` of `src/app/session.ts`) opens the empty window
  on the click, as before (a browser blocks a window that a click does not open), posts the
  init, sends the window to its `url` and asks the auth endpoint until the store is signed
  in. A failed init closes the window and shows its error on the login screen.

## The checks

- **C005** (warning): the Google login of the contract is the `GET` of bazis-authing 2.7 or
  older, for which the login screen has no button; its fix is
  `pip install -U 'bazis-authing>=2.8.0'` and the export of the contract. The capability
  `authing` keeps its minimum 2.6.0 (`C004`): a product with the password login only has
  no issue with bazis-authing 2.6 or 2.7.

## The tests of the package

- The `test` extra requires `bazis-authing>=2.8.0` (it required 2.7.0): the sample and its
  end-to-end tests run against the protocol that the template follows. bazis-authing 2.8
  requires `bazis>=2.19.0`, so the `lowest-direct` job of CI installs bazis 2.19.0, not
  2.17.0; the package itself keeps `bazis>=2.17.0` (the aggregates of the core are all it
  needs) and does not depend on bazis-authing.

## Migrating from 0.6

```bash
pip install -U bazis-front "bazis-authing>=2.8.0"   # bazis-authing 2.8 requires bazis 2.19
python manage.py bazis_front update
python manage.py bazis_front contract    # contract.json of format 10
python manage.py bazis_front check
cd frontend && npx tsc --noEmit && npm run lint && npm test && npm run build
```

1. `contract.json` is of format 10: `check` reports `C002` until it is exported again. With
   bazis-authing 2.7 or older and its Google service, `check` warns (`C005`) after it.
2. `update` merges `src/app/session.ts`, `src/app/session.test.ts` and the client. A product
   that changed them keeps its changes in the merge; the window must open the `url` of
   `api.authInit`, never `<url>?<token_param>=<store>`.
3. A code of the product that read `CAPABILITIES.authing.token_param` no longer compiles: the
   Google login of bazis-authing 2.8 takes no store token in its URL; call `loginInWindow`.
4. A frontend served apart from its API checks that both are on one site and that the API
   answers CORS with credentials (`BS_CSRF_TRUSTED_ORIGINS`), then signs in with Google
   once: a 400 in the window is a ticket without its cookie.
